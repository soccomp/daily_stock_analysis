- Codex model: **Terra**

## Owner Goal

Produce a decision-quality answer to two questions:

1. **Can the current local Qwen be used reliably in DSA Research?**
2. **Is it good enough for the current production Research role, or is a paid cloud-model A/B trial justified?**

The final report must be decisive on practical usability even if actionable-long evidence remains sparse. It may say “usable with limitations”; it must not hide behind “insufficient evidence” for dimensions that can already be measured.

Do **not** enable or purchase any cloud model in this mission.

## Scope

This mission has two parts:

1. repair or replace the **evaluation harness only** so an offline Analyzer replay can reliably return a sanitized final `AnalysisResult` to the evaluator;
2. produce a final local-Qwen usability scorecard using existing natural-cycle/history evidence plus, only if necessary, at most **2 new local-only Analyzer replays** after the harness is proven observable.

No production behavior change is intended.

## Phase A — Diagnose the Missing Replay Result Without New Model Calls

First reproduce the evaluation harness control flow **without calling Qwen**.

Trace:

`persisted Research context -> evaluator/harness -> Analyzer call wrapper -> result/exception/timeout -> serialization -> parent process/report`

Determine exactly why PR #17’s two replay attempts produced no inspectable serialized `AnalysisResult`.

Check, as applicable:

- subprocess timeout / parent timeout;
- child exit code / signal;
- stdout/stderr capture;
- exception serialization;
- result serialization incompatibility;
- process termination before flush;
- telemetry/database monkeypatch side effects;
- async/event-loop/process isolation issues;
- oMLX request timeout versus evaluator timeout;
- wrapper code swallowing a valid Analyzer return or exception.

Use a deterministic mocked/stubbed Analyzer result to prove the harness can transport and serialize a full sanitized `AnalysisResult` before making any new Qwen request.

If the defect can be resolved only by changing production `src/` behavior, stop at:

`ARCHITECTURE REVIEW GATE — PRODUCTION_SOURCE_CHANGE_REQUIRED`

## Phase B — Practical Local-Qwen Scorecard From Existing Evidence

Before any new model calls, build the smallest sufficient scorecard from existing persisted/runtime evidence generated by the current local route.

Use a bounded evidence window: newest **30 completed local-Qwen Research analyses/cycles**, or fewer if enough to establish the dimension.

Measure separately:

### 1. Route / operational usability

- route availability and observed successful completions;
- hard generation failures/timeouts attributable to the local route;
- generation latency where attributable from logs/runtime evidence;
- whether latency materially blocks DSA after the already-fixed Snapshot refresh architecture.

### 2. Structured-output usability

- parse/schema success rate where observable;
- bounded completion/repair frequency where observable;
- missing required structured fields;
- ambiguous/unknown action frequency;
- whether completed Research can persist as valid `AnalysisResult`.

### 3. Research decision distribution

Report the normalized action distribution (`buy/add/watch/hold/avoid/alert/reduce/sell/unknown`) factually.

Do **not** treat a high `watch/hold` rate by itself as model failure.

### 4. Actionable-long quality

For every naturally existing scoreable `buy/add` sample, check:

- `entry > 0`
- `stop > 0`
- `target > 0`
- `stop < entry`
- `target > entry`
- no downstream clamping/reordering/fabrication
- parser/schema/integrity success
- reaches the current Research -> Brain actionable-plan gate without model-produced structural failure.

If zero naturally existing actionable samples remain, state that clearly and continue to Phase C only after Phase A harness proof.

## Phase C — At Most 2 New Local Replays, Only After Harness Proof

Run only if all are true:

- Phase A harness transport/serialization is demonstrably fixed;
- existing evidence still lacks at least two scoreable actionable-long samples;
- a suitable persisted Research-only bullish candidate context exists.

Limits:

- **maximum 2 new local Qwen Analyzer calls total**;
- current production Analyzer path and current oMLX/Qwen model/config only;
- no prompt/model tuning;
- no Bocha/search refresh;
- no synthetic bullish forcing;
- no PortfolioSnapshot/account/RiskPolicy/Brain/execution data in LLM input;
- no scheduler cycle;
- no broker/execution call;
- only the existing one bounded completion/repair behavior.

For each replay, the harness must capture:

- exit/transport status;
- total latency;
- parser/schema/integrity result;
- final normalized action;
- sanitized `entry/stop/target` if present;
- repair/completion count if observable;
- exact model-output structural failure, if any.

If replay returns `watch/hold`, that is a valid sample for general usability but not an actionable-long score. Do not force another direction beyond the two-call cap.

## Final Usability Verdict — Required

The report must choose exactly one **practical usability verdict**:

### `LOCAL_QWEN_GOOD_FOR_CURRENT_RESEARCH`
Use only if route reliability, structured-output quality, and latency are acceptable for the current production Research role, with no material repeated model-output defect. Actionable evidence should be adequate or limitations demonstrably low-risk.

### `LOCAL_QWEN_USABLE_WITH_LIMITATIONS`
Use when the model demonstrably works in current DSA Research but has meaningful limitations such as high latency, frequent bounded repair, sparse actionable evidence, or inconsistent structured details that remain safely contained by deterministic/fail-closed architecture.

### `LOCAL_QWEN_NOT_GOOD_ENOUGH_FOR_CURRENT_RESEARCH`
Use only if repeated evidence shows material model-output or operational weakness that makes the current Research role unreliable despite existing safety gates.

Also choose exactly one cloud decision:

- `NO_PAID_CLOUD_TRIAL_NEEDED`
- `PAID_CLOUD_A_B_TRIAL_JUSTIFIED`
- `CLOUD_TRIAL_OPTIONAL_NOT_REQUIRED`

The report must answer in plain language:

- **能不能用：能 / 不能**
- **好不好用：好用 / 能用但有明显限制 / 不好用**
- the top 3 evidence-backed reasons;
- whether the Owner should spend money on a cloud A/B trial now.

Do not use `INSUFFICIENT_ACTIONABLE_EVIDENCE` as the only final conclusion. Sparse actionable evidence may remain a limitation, but practical usability must still be judged from the broader evidence.
